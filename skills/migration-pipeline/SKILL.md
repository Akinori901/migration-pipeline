# 移行パイプライン（1ドメイン分）

フロントが呼んでいるエンドポイントが新システムに無い、という状況を
**原因別に切り分けてから対処する**ための手順。

## 入力

次のいずれか。

- ドメイン名（例: `orders`, `items`）
- 画面パス（例: `/sales/orders`）
- エンドポイントパス（例: `/api/v1/orders`）

## 不一致の原因タグ

フロントが呼ぶパスが新システムに無い場合、原因は**単独または複合**で存在します。
対処を決める前に、必ずこのタグを付けます。

| タグ | 原因 | 対処 |
|------|------|------|
| `[FE変更漏れ]` | フロントがまだ旧システムのパスを呼んでいる | フロント側を修正 |
| `[BE欠損]` | 新システムにそのエンドポイントが未実装 | 新システムに実装 |
| `[パス変更]` | 新システムでパスが変わり、フロントが未追従 | **ユーザー判断** → FE修正 or 新側にエイリアス |
| `[ロジック欠落]` | エンドポイントはあるが、バリデーション・権限・エラー処理・副作用が欠落 | **ユーザー承認後**に補完実装 |
| `[正常]` | 両側で対応済み・一致 | 対処不要 |

**このタグ付けが手順の中心です。**
「パスが無い」だけでは、フロントを直すのか新システムに実装するのか決まりません。
原因を切り分けずに対処すると、片側だけ直して不整合が残ります。

## 実行フロー

```
トリアージフェーズ（並行 → 合流 → 三角照合）
────────────────────────────────────

Step 1（並行実行）
  fe-analyst      — フロントが実際に呼んでいるエンドポイントと期待レスポンスを抽出
  legacy-analyst  — 旧システム側の契約（パラメータ・バリデーション・レスポンス）を抽出
  service-router  — 新システム側の既存エンドポイントを抽出（service-contract.md）

Step 2（順次 — Step 1 の3出力を入力）
  schema-architect — 三者を突き合わせ、不一致に原因タグを付与し、確定API契約を設計

Step 2.5（順次・2段 — 非正常系の欠落検出）
  legacy-analyst   — 旧システムのバリデーション・権限・エラー処理・副作用を洗い出す
  schema-architect — 新システム側に欠落している考慮に [ロジック欠落] を付与

Step 3（順次）
  service-router   — タグ別に、どのサービスへ実装すべきかを判定

  → ユーザー承認後に対処フェーズへ


対処フェーズ（原因タグ別に分岐）
────────────────────────────────

Step 4 は二段階（計画 → 承認 → 実行）で行う:
  ① planner が対処計画を作成（変更ファイル・参照パターン・影響範囲・検証手順を明示 → plan.md）
  ② ユーザー承認
  ③ 実行:
     [FE変更漏れ]   — fe-engineer がフロント側のパスを修正
     [BE欠損]       — be-engineer が新システムにエンドポイントを実装
     [パス変更]     — ユーザー判断に従い上記どちらかを実行
     [ロジック欠落] — be-engineer が非正常系を補完実装


検証フェーズ（並行実行）
────────────────────────

Step 5（並行実行）
  contract-verifier    — 確定仕様 vs 実装コード の差分検出
  integration-verifier — フロントの期待値 vs 実装コード の接続検証
```

## 設計上の要点

- **三角照合する。**
  フロント・旧システム・新システムの3点を突き合わせます。
  2点だけでは「フロントが古いのか、新システムが未実装なのか」が判別できません。
- **計画と実行を分ける。**
  対処が自明に見える場合でも、変更ファイルと検証手順を計画として書き出してから承認を取ります。
  移行では「自明に見えて実は影響範囲が広い」変更が頻出します。
- **非正常系を別ステップで見る。**
  正常系のレスポンスが一致していても、バリデーションや権限チェックが落ちていることがあります。
  ここは意識して探さないと見つかりません。
- **成果物はファイルに出す。**
  各エージェントの出力はファイルへ書き、次のエージェントはそれを読みます。
  会話に全文を載せないことで、長いパイプラインでもコンテキストが保ちます。
